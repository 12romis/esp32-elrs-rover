# Ровер ESP32-S3 — повний контекст для розробки прошивки

**Версія документа:** 2026-10-15
**Призначення:** єдине джерело контексту для агента, який реалізує прошивку по SDD (spec-driven development).
**Мова коду:** C, ESP-IDF **v6.1** (поточна стабільна), FreeRTOS.

---

## 0. Як користуватися цим документом

Цей документ — **контракт між залізом і прошивкою**. Усе в розділах 1–4 витягнуто з реального `kicad-rover.net` і є обовʼязковим. Розділи 5–9 — рекомендована реалізація; агент може запропонувати краще, але мусить обґрунтувати.

**Пріоритет джерел при конфлікті:**
1. `kicad-rover.net` / `kicad-rover.kicad_pcb` — фізичне залізо, оскарженню не підлягає
2. Цей документ
3. Будь-що інше

**Розділ 9 містить невідомі величини, які фізично неможливо дізнатися з файлів.** Вони мають бути винесені в конфіг як константи з явними `TODO` і заповнені після вимірювання на залізі. Агент **не має права вигадувати для них значення**.

**Порядок робіт — у розділі 7, і він двоступеневий.** Спершу передфази **P0–P7** (підрозділ 7.0): маленькі викидні діагностичні прошивки, єдина мета яких — перетворити «?» з розділу 9 на числа. Тільки після них починаються фази 0–7 власне прошивки, які ведуться по **SDD** (підрозділ 7.0.1). Головне правило всього документа: **специфікація фази не пишеться, доки її вхідні константи невідомі.**

## 1. Апаратна платформа

### 1.1 Загальна архітектура

4-колісний ровер із танковим приводом (skid-steer). Плата-носій 100×100 мм, 2 шари, усі активні модулі в гніздах.

```
2S Li-ion 8.4 В
  → запобіжник (поза платою) → вимикач → XT30 (J1)
  → D1 P6KE12A (TVS) → C3 1000 мкФ
  ├─ U1 MP1584EN → 5.40 В → D2 (SS34, −0.4 В) → шина +5V (5.0 В) → C27 470 мкФ
  │    └─ ESP32 (вивід 5V) → власний LDO платки → +3V3_MCU
  │    └─ ELRS (J7), зумер (BZ1), світлодіоди
  ├─ U2 MP1584EN → 3.30 В → шина +3V3_PERIPH
  │    └─ PCF8574 (U6), 4× VL53L0X, 4× ENC_VCC, VCC драйверів
  ├─ U4, U5 TB6612FNG — VM напряму від VBAT
  └─ J4 — FPV AIO камера/передавач, напряму від VBAT (керування ВИДАЛЕНО)
```

**Дві окремі шини 3.3 В — навмисно.** `+3V3_MCU` приходить з LDO платки ESP32 і живить тільки сам мікроконтролер. `+3V3_PERIPH` — з окремого понижувача U2, живить усю периферію. Зроблено тому, що LDO платки не витягував 4 далекоміри (до 160 мА імпульсами) разом із Wi-Fi.

### 1.2 Мікроконтролер

- Модуль **YD-ESP32-S3** (VCC-GND Studio), ESP32-S3 **N16R8**
- 16 МБ flash, 8 МБ **octal** PSRAM
- Консоль і прошивка — через **нативний USB (USB Serial/JTAG)**, не через UART0
- RGB-світлодіод платки на **GPIO48** (перевірено на реальній платі), у схемі не задіяний

### 1.3 Радіоканал

| | |
|---|---|
| Пульт | **RadioMaster TX12** (EdgeTX) |
| Приймач | **BetaFPV ELRS Nano RX, 2.4 ГГц**, у роз'ємі J7 |
| Протокол | CRSF по UART |
| Живлення приймача | **5 В** — збігається з J7.1 на платі ✓ |
| Антена | U.FL + T-антена |

**Версії мають збігатися.** Приймач і TX-модуль повинні працювати на одній мажорній версії ELRS, інакше звʼязку не буде взагалі. BetaFPV постачає Nano з прошивкою 3.3.0 і рекомендує оновити обидві сторони до неї. Перевір, яка версія в TX12: він буває з внутрішнім 4-in-1 мультипротокольним модулем (тоді ELRS треба зовнішнім) і з внутрішнім ELRS.

**Привʼязка:** увімкнути й вимкнути живлення приймача три рази поспіль — швидке подвійне блимання означає режим привʼязки. Далі натиснути Bind на пульті. Суцільне світло = привʼязано, стан зберігається.

**Розкладка каналів.** EdgeTX за замовчуванням видає **AETR**:

| Канал CRSF | EdgeTX | Для ровера |
|---|---|---|
| 1 | Aileron (правий стік, X) | **поворот** (steer) |
| 2 | Elevator (правий стік, Y) | **тяга вперед/назад** (throttle) |
| 3 | Throttle (лівий стік, Y) | не використовувати — він з фіксатором, не самоцентрується |
| 4 | Rudder (лівий стік, X) | резерв |
| 5 | AUX1 (зазвичай SA) | **ARM / DISARM** |
| 6 | не призначений на пульті | резерв |
| 7 | не призначений на пульті | резерв |
| 8 | трипозиційний перемикач | **фари** (підтверджено P5; замість CH6 із початкового плану) |

Канал 3 (throttle) свідомо не використовується як тяга: на TX12 цей стік має тріщотку й не повертається в центр, тому при втраті уваги ровер не зупиниться. Тяга йде на самоцентрований правий стік.

**ARM — тільки трипозиційний або двопозиційний тумблер, ніколи не кнопка.** І arm має спрацьовувати лише при нейтральних стіках: інакше ровер стрибне з місця, якщо тумблер клацнули з відхиленим стіком.

### 2.1 Карта портів PCF8574 (U6)

| Біт | Порт | Підключено | Логіка |
|---|---|---|---|
| 0 | P0 | XSHUT **U7** (ToF) | 1 = сенсор увімкнений |
| 1 | P1 | XSHUT **U8** | 1 = увімкнений |
| 2 | P2 | XSHUT **U9** | 1 = увімкнений |
| 3 | P3 | `/LIGHT_EN` → Q3 → фари J2, J3 | **1 = фари ГОРЯТЬ** |
| 4 | P4 | XSHUT **U10** | 1 = увімкнений |
| 5 | P5 | `/STOP_RED` → Q5 → J5.1, J6.1 | **1 = червоне ГОРИТЬ** |
| 6 | P6 | `/STOP_GREEN` → Q4 → J5.3, J6.3 | **1 = зелене ГОРИТЬ** |
| 7 | P7 | не підключений | вільний |

**Зверни увагу: XSHUT U10 сидить на P4, а не на P3.** Біти не йдуть підряд — це наслідок перестановки під час розводки.

### 2.2 Прив'язка моторів до драйверів

| Мотор | Роз'єм | Драйвер | Канал | Виходи |
|---|---|---|---|---|
| перед-лівий | M1 | U4 | A | AO1→M+, AO2→M− |
| зад-лівий | M2 | U4 | B | BO1→M+, BO2→M− |
| перед-правий | M3 | U5 | **B** | BO1→M+, BO2→M− |
| зад-правий | M4 | U5 | **A** | AO1→M+, AO2→M− |

Канали A/B дзеркально переставлені між U4 і U5. **Функціонально це не має значення**, бо на платі `PWMA=PWMB`, `AIN1=BIN1`, `AIN2=BIN2` — обидва канали драйвера завжди отримують однакову команду. Один логічний канал на борт.

**Наслідок для прошивки: незалежне керування окремим колесом фізично неможливе.** Тільки `speed_left` і `speed_right`.

## 3. Шини живлення — числа для прошивки

| Шина | Напруга | Джерело | Споживачі |
|---|---|---|---|
| `+VBAT` | 6.0–8.4 В | 2S Li-ion | VM драйверів, U1, U2, FPV |
| `+5V` | 5.0 ± 0.1 В | U1 (5.40 В) − D2 | ESP32, ELRS, зумер, світлодіоди |
| `+3V3_MCU` | 3.25–3.30 В | LDO платки ESP32 | тільки MCU |
| `+3V3_PERIPH` | 3.25–3.30 В | U2 | PCF8574, 4× ToF, енкодери, VCC драйверів |

### 3.1 Дільник вимірювання батареї

```
+VBAT ── R1 (100k) ──┬── R4 (33k) ── GND
                     └── C4 (100 нФ) ── GND
                     └── GPIO1 (ADC1_CH0)
```

Коефіцієнт: `Vbat = Vadc × (100 + 33) / 33 = Vadc × 4.0303`

**Виміряно на платі: k = 4.0433** (вольтметром на TP1 і GPIO1, 15.10.2026).

Поправка на вхідний опір вольтметра: 10 МОм паралельно R4 робить нижнє плече 32.89 кОм замість 33, тому прилад мусить показувати 4.0403 навіть при ідеальних резисторах. Виміряні 4.0433 відрізняються від цього на +0.07 %, тобто резистори практично номінальні, а справжній коефіцієнт — **4.033**.

Брати в код **4.033**. Це лише початкове значення: домінуюча похибка тут не резистори, а сам ADC (±2–3 % навіть із curve-fitting калібруванням), тому остаточне калібрування робиться двома точками через ADC і зберігається в NVS — див. нижче.

| VBAT | На ADC |
|---|---|
| 8.4 В (повний) | 2084 мВ |
| 7.4 В (номінал) | 1836 мВ |
| 6.6 В (низький) | 1637 мВ |
| 6.0 В (відсічка) | 1489 мВ |

**Послаблення: `ADC_ATTEN_DB_12`** (діапазон 0–3100 мВ). Інші варіанти не підходять: при 6 dB стеля 1750 мВ, а треба 2084.

Фільтр R‖C: 24.8 кОм × 100 нФ → зріз 64 Гц. Вимірювати не частіше 5 Гц, усереднювати 16–64 відліки.

## 4. Обмеження заліза, які диктують архітектуру ПЗ

Це не поради, а фізичні факти. Порушення кожного з них дає дефект, який важко діагностувати.

### 4.1 PCNT: рівно 4 юніти, і всі зайняті

ESP32-S3 має **4 юніти PCNT**, по 2 канали кожен. Квадратурний енкодер займає один юніт цілком. Чотири енкодери = чотири юніти. **Вільних PCNT не лишається.**

### 4.2 LEDC: 8 каналів, 4 таймери, тільки low-speed

ESP32-S3 не має групи high-speed. Потрібно: 2 канали на мотори (спільний таймер, 20 кГц) + 1 канал на зумер (окремий таймер, змінна частота). Разом 3 канали, 2 таймери. Запас великий.

### 4.3 Стан PCF8574 одразу після подачі живлення

Після POR **усі виводи PCF8574 у високому стані**. Це означає до першої I²C-транзакції:

- P3, P5, P6 = 1 → **фари і обидва задні ліхтарі (червоний + зелений одночасно) горять**
- P0, P1, P2, P4 = 1 → **усі чотири далекоміри активні на заводській адресі 0x29** → конфлікт на шині

**Перша I²C-операція прошивки має бути запис `0x00` у PCF8574.** Це одночасно гасить усе світло й утримує всі XSHUT у низькому стані, тобто дає визначену стартову точку для процедури призначення адрес.

### 4.4 Квазідвонаправлені виводи PCF8574

Вивід у високому стані дає лише ~100 мкА підтяжки. Саме тому схема побудована так, що струм у базу транзистора подає зовнішній резистор (R7, R10, R13 на `+3V3_PERIPH`), а PCF8574 його **забирає**. Для прошивки наслідок простий: логіка **не інвертована**, 1 = увімкнено. Але знати механізм треба, бо «просто підняти пін» тут означає «відпустити лінію».

### 4.5 STBY — апаратний failsafe

`GPIO21` має зовнішню притяжку R16 10k до GND. Поки прошивка не підняла його свідомо, обидва драйвери в standby, виходи Hi-Z, мотори вільні. Це працює при скиданні, до завантаження прошивки й при зависанні, якщо GPIO переходить у Hi-Z.

**Прошивка зобовʼязана:** опускати STBY у 0 при будь-якому переході в DISARMED / FAILSAFE / FAULT.

> Виняток фази 0: прошивка фази 0 не налаштовує STBY і покладається на R16 (ADR-0003 у `docs/features/phase0-skeleton/adr/`). Виконання цієї вимоги переходить у фазу 1 (`drive`).

### 4.6 I²C — одна шина, довгі шлейфи

На `GPIO8/GPIO9` висять PCF8574 і чотири далекоміри. Далекоміри підключаються **шлейфами JST 15–20 см**, а не в гнізда: U7–U10 на платі — це роз'єми, не сокети. Те саме стосується моторів M1–M4 і світла J2/J3/J5/J6. У гніздах сидять лише U1, U2 (MP1584EN), U3 (YD-ESP32-S3), U4, U5 (TB6612) і U6 (PCF8574).

**Підтяжки I²C.** R17/R19 (4.7 кОм на `+3V3_PERIPH`) на платі навмисно **не встановлені** — DNP. Перевірка 15.10.2026 показала 3.3 В на TP6 і TP7 при під'єднаному лише PCF8574 і повністю відключених далекомірах, тобто **підтяжки дає сам модуль PCF8574** (типово 10 кОм на платі модуля). Наслідки для прошивки:

- шина робоча навіть без жодного далекоміра — скан знайде PCF8574 ізольовано, без конфлікту адрес;
- при під'єднанні чотирьох далекомірів (ще по ~10 кОм кожен) сумарна підтяжка падає до ~2 кОм, що на 100 кГц абсолютно нормально;
- встановлювати R17/R19 не потрібно.

**Частота: 100 кГц. Не піднімати до 400 кГц.** На розводці лінії I²C стрибають між шарами близько десятка разів; на 100 кГц запас величезний, на 400 кГц його вже немає.

### 4.7 Чотири VL53L0X з однаковою заводською адресою

Усі приходять на 0x29. Послідовність ініціалізації обовʼязкова:

1. Записати `0x00` у PCF8574 → всі XSHUT низькі, всі сенсори в скиданні
2. Підняти XSHUT першого (біт 0) → чекати ≥2 мс → ініціалізувати → **перепризначити адресу** на 0x30
3. Підняти біт 1 → ініціалізувати → 0x31
4. Біт 2 → 0x32
5. Біт 4 (не 3!) → 0x33

Нова адреса живе тільки до скидання живлення сенсора, тому процедуру треба повторювати при кожному старті.

### 4.8 Енкодери в одному шлейфі з моторними дротами

Лінії A/B фізично йдуть поруч зі щітковими дротами. Наведення вже сталося в кабелі, розводка плати цього не виправить.

**Обовʼязково вмикати апаратний glitch-фільтр PCNT** (`max_glitch_ns ≈ 1000`).

## 5. Обсяг прошивки — що має бути реалізовано

Це функціональний мінімум робочого ровера. Нічого зайвого тут немає: кожен пункт або потрібен для руху, або рятує залізо.

| Підсистема | Що саме |
|---|---|
| Задачі | FreeRTOS, 5–6 задач, розділення по ядрах |
| Планування | жодних блокуючих затримок у логіці: `vTaskDelayUntil`, черги з таймаутом, подієві UART/PCNT. `esp_rom_delay_us` допустима лише в драйвері ToF для 2-мс паузи після XSHUT |
| Стани | явний `rover_state_t`, таблиця переходів, лог кожного переходу |
| Модульність | `components/` — по компоненту на підсистему, жодних номерів GPIO поза `board_pins.h` |
| Аналогове | ADC (батарея), LEDC PWM (мотори, зумер) |
| Цифрове | UART (CRSF), I²C (ToF, PCF8574) |
| Переривання | PCNT watch-point callback, UART event queue, GPTimer alarm |
| Обмін між задачами | FreeRTOS черги, нічого через глобальні змінні |
| Синхронізація | `m_i2c` (спільна шина), `m_state` (спільна структура). Уся спільна памʼять — тільки через чергу або під мʼютексом |
| Зворотний звʼязок | енкодери → реальна швидкість борту |
| Регулювання | PID по швидкості на кожен борт |
| Налаштування | коефіцієнти PID у NVS + консольні команди для зміни на льоту |
| Граничні умови | saturation виходу PID, anti-windup інтегратора, акумуляція переповнення PCNT, кліп значень CRSF |
| Watchdog | Task WDT, підписані всі періодичні задачі |
| Помилки периферії | перевірка `esp_err_t` скрізь; реакція на NACK I²C; таймаут CRSF; деградація при відмові одного ToF |
| Валідація вводу | CRC8 кадру CRSF, перевірка довжини, діапазон каналів, відсів викидів ToF |
| Поведінка при збої | будь-яка помилка → перехід у FAILSAFE/FAULT, ніколи не `abort()` |

Корисне доповнення за десяток рядків: вимір часу такту керування через `esp_timer_get_time()` і вивід у телеметрію — показує, що CPU не перевантажений, і допомагає при налагодженні PID.

## 6. Рекомендована архітектура

### 6.1 Задачі

| Задача | Пріор. | Ядро | Період | Призначення |
|---|---|---|---|---|
| `crsf_rx` | 6 | 1 | подієва | читає UART2, парсить кадри, валідує CRC, кладе канали в `q_rc` |
| `control` | 5 | 1 | 20 мс (50 Гц) | state machine, мікшер, PID, запис у LEDC/DIR/STBY |
| `sensors` | 3 | 0 | 50 мс | опитування 4× VL53L0X по I²C, фільтрація, `q_tof` |
| `ui` | 2 | 0 | 100 мс | PCF8574: фари, стоп-сигнали; зумер |
| `telemetry` | 2 | 0 | 200 мс | ADC батареї, лічильники, лог, CRSF-телеметрія назад |
| `console` | 1 | 0 | блокується на вводі | команди налаштування через USB |

Розділення по ядрах навмисне: керування і радіо на core 1, усе решта на core 0 разом із Wi-Fi-стеком (якщо він буде).

### 6.2 Черги і мʼютекси

```c
QueueHandle_t q_rc;    // crsf_rx  -> control   (rc_channels_t, довжина 4, overwrite)
QueueHandle_t q_tof;   // sensors  -> control   (tof_set_t, довжина 2)
QueueHandle_t q_ui;    // control  -> ui        (ui_cmd_t, довжина 8)
QueueHandle_t q_tel;   // будь-хто -> telemetry (tel_item_t, довжина 16)

SemaphoreHandle_t m_i2c;    // шина спільна: PCF8574 + 4× ToF
SemaphoreHandle_t m_state;  // rover_state_t читається кількома задачами
```

Для `q_rc` використовувати `xQueueOverwrite` з довжиною 1: керуванню потрібен **останній** стан стіків, а не черга застарілих.

### 6.3 Машина станів

```
          ┌──────┐
          │ BOOT │  ініціалізація драйверів, NVS
          └──┬───┘
             v
       ┌───────────┐
       │ SELFTEST  │  скан I²C, енумерація ToF, перевірка батареї
       └─┬───────┬─┘
    ok   │       │  critical fail
         v       v
   ┌──────────┐ ┌───────┐
   │ DISARMED │ │ FAULT │  STBY=0, зумер, червоне блимає
   └─┬──────┬─┘ └───────┘
 arm │      ^ disarm
     v      │
   ┌──────────┐      перешкода       ┌───────────────┐
   │  ARMED   │ <------------------> │ OBSTACLE_HOLD │
   └─┬────────┘                      └───────┬───────┘
     │                                       │ disarm (фаза 6: пара OBSTACLE_HOLD → DISARMED)
     │ втрата CRSF > 500 мс  або  VBAT < 6.0 В  (з ARMED і з OBSTACLE_HOLD)
     v
   ┌──────────┐
   │ FAILSAFE │  STBY=0, гальмування, зумер, червоне
   └──────────┘
```

Фаза 6: OBSTACLE_HOLD досяжний лише з ARMED; із нього можна повернутися в ARMED (сектор вільний), роззброїтися в DISARMED одним переходом
або піти у FAILSAFE за тими ж причинами, що й з ARMED. Таблиця має 12 дозволених пар із 49 (ADR-0004 phase6-tof).

Умови `arm`: канал arm на пульті високий **І** стіки в нейтралі **І** CRSF живий **І** батарея в нормі. Інакше arm ігнорується (це пункт 5.3).

### 6.4 Структура репозиторію

```

├── sdkconfig.defaults
├── README.md                    ← опис, запуск, архітектура
├── docs/
│   ├── architecture.md          ← блок-схема, 1.4 / 8.2
│   ├── pinout.md                ← копія розділу 2 цього документа
├── main/
│   └── main.c                   ← тільки init + старт задач
├── components/
│   ├── board/        board_pins.h   ← ВСІ номери GPIO, єдине місце
│   ├── app_state/    машина станів: таблиця переходів, історія (фаза 0)
│   ├── rover_console/ консоль через USB: команди, права за станом (фаза 0; не `console` — це компонент ESP-IDF)
│   ├── watchdog/     Task WDT з panic, задача heartbeat, причина скидання (фаза 0)
│   ├── storage/      NVS: ініціалізація й політика очищення (фаза 0)
│   ├── drive/        мотори: LEDC, DIR, STBY, мікшер
│   ├── encoders/     PCNT ×4, швидкість, одометрія
│   ├── pid/          регулятор зі saturation і anti-windup
│   ├── crsf/         парсер CRSF, CRC8, failsafe-таймер
│   ├── ioexp/        PCF8574: тіньовий регістр, bit-API
│   ├── tof/          VL53L0X ×4, послідовність XSHUT
│   ├── battery/      ADC + калібрування + усереднення
│   ├── ui/           фари, стоп-сигнали, зумер
│   └── telemetry/    лог, CRSF назад
├── test/host/                       ← тести чистої логіки, звичайний gcc
└── tools/bringup/                   ← діагностичні прошивки P0–P7 (7.0)
```

**`components/board/board_pins.h` — єдине місце, де є номери GPIO.** Жоден інший файл не містить літералів пінів. Це дозволить за хвилину виправити помилку, якщо щось у розводці виявиться не таким.

#### Розділення на чисту логіку і HAL — обовʼязкове

Кожен компонент зі списку вище ділиться на **два файли**: `<name>_core.c` без жодного `#include` з ESP-IDF (тільки `stdint.h`, `stdbool.h`, `string.h`) і `<name>_hal.c`, який викликає драйвери.

| Чиста логіка (`_core.c`) — тестується на хості | HAL (`_hal.c`) — перевіряється тільки на залізі |
|---|---|
| мікшер танкового приводу, нормалізація | LEDC, GPIO напрямків, STBY |
| парсер CRSF: CRC8 `0xD5`, розпаковка 16×11 біт, мапінг у мкс | UART2, таймер failsafe |
| PID із saturation і anti-windup | PCNT, читання лічильників |
| переходи машини станів | I²C-транзакції |
| перерахунок ADC → мВ → VBAT, усереднення | `esp_adc` oneshot |
| тіньовий регістр PCF8574 (read-modify-write у памʼяті) | запис байта в шину |
| перерахунок лічильників в оберти/с і одометрію | послідовність XSHUT |

**Навіщо саме так.** Ліва колонка — це більша частина логіки, де водяться справжні помилки (знак, переповнення 16-бітного лічильника, CRC, межі діапазону), і вона перевіряється без плати, за секунду, у циклі. Права колонка — тонкий шар виклику драйверів, у якому тестувати нічого: «перевірити, що `ledc_set_duty` викликано з таким аргументом» — це тест на мок, а не на поведінку, і він не ловить жодної реальної несправності.

`test/host/` компілюється **звичайним gcc** (не `idf.py --preview set-target linux`): файли `_core.c` не містять заголовків ESP-IDF, тому збираються будь-де. Хостовий режим ESP-IDF лишається експериментальним, а драйвери в ньому все одно лише мокаються, тож залежати від нього тут нема сенсу.

## 7. Фазовий план реалізації

Порядок узгоджений із порядком bring-up заліза: кожна фаза тестується на тому обладнанні, яке на цей момент уже вставлене в гнізда.

План складається з двох різних за природою частин:

- **передфази P0–P7 — діагностичні прошивки.** Це вимірювальні інструменти, а не продукт. Їхній єдиний результат — числа, які заповнюють таблицю розділу 9. Вони **не проєктуються по SDD**, не мають специфікації, не йдуть у фінальний репозиторій і не підлягають рев'ю якості коду;
- **фази 0–7 — власне прошивка.** Вони проєктуються по SDD (див. 7.0) і починаються лише тоді, коли відповідні передфази дали числа.

---

### 7.0 Передфази P0–P7 — діагностичні прошивки до початку розробки

**Призначення.** Таблиця розділу 9 містить десять величин, яких немає у файлах і які агент не має права вигадати. Поки вони «?», будь-яка специфікація фази, що на них опирається, буде специфікацією на вигаданому фундаменті. Передфази існують, щоб перетворити «?» на числа **раніше**, ніж буде написаний рядок коду фінальної прошивки.

**Де живуть.** Окремі незалежні ESP-IDF-проєкти в `tools/bringup/pNN_<name>/`, кожен зі своїм `main.c` на 50–200 рядків. Вони **не є** компонентами основного застосунку і не підключаються до нього. Після зняття показників їх можна лишити в репозиторії як доказ методики (це корисно для захисту) або видалити — на архітектуру вони не впливають.

**Куди пишеться результат.** Один файл `docs/measured.md` у форматі «константа — значення — як отримано — дата». Саме він, а не чат і не пам'ять, є джерелом для заповнення розділу 9 і для `calib.h`.

**Правило зупинки.** Передфаза вважається пройденою, тільки коли її число **записане у `docs/measured.md`**. «Подивився в консоль і запам'ятав» не рахується.

#### P0 — тулчейн, чіп, PSRAM

**Залізо:** плата з U3, живлення від USB. Решта може бути не під'єднана.
**Прошивка:** `hello_world` плюс чотири рядки логу: `esp_chip_info()`, розмір флешу, `esp_psram_get_size()`, `esp_get_free_heap_size()`.
**Що вирішує:** чи правильно налаштований `sdkconfig` під N16R8. Octal PSRAM не визначається «сама собою» — потрібні явні опції (див. 8.6), і при неправильній конфігурації плата або не завантажується, або молча працює без 8 МБ.
**Приймання:** у логу `ESP32-S3`, флеш `16MB`, PSRAM `8388608` байт. Якщо PSRAM = 0 — зупинитись і правити `sdkconfig`, а не йти далі.
**Заповнює:** нічого з розділу 9, але знімає найтиповішу причину згаяного вечора на старті.

#### P1 — скан I²C

**Залізо:** + U6 у гнізді. **Далекоміри від'єднані** — це принципово.
**Прошивка:** `i2c_master`, 100 кГц, цикл по `0x20…0x27`, друк знайдених.
**Що вирішує:** `PCF8574_ADDR` (конфлікт 10.1) — остаточно й однозначно, бо на шині рівно один пристрій.
**Приймання:** знайдено **рівно одну** адресу в діапазоні. Дві або нуль — це помилка монтажу або живлення, не повод вгадувати.
**Заповнює:** `PCF8574_ADDR`.

#### P2 — виходи PCF8574 і світло

**Залізо:** + фари в J2/J3, задні в J5/J6.
**Прошивка:** запис `0x00` першою ж операцією, потім по колу вмикати по одному біту з паузою 1 с, друкуючи назву каналу.
**Що вирішує:** чи правильна карта бітів із 2.1 (P3 = фари, P5 = червоний, P6 = зелений), чи зрозуміла квазідвонаправлена логіка (4.4), і чи правильно розпаяні самі світлодіоди.
**Приймання:** при подачі живлення світло **не загоряється** (це доказ, що `0x00` дійшов); далі кожен із трьох каналів вмикається окремо й незалежно.
**Заповнює:** підтверджує 2.1. Якщо карта не збіглася — виправити розділ 2.1, бо далі по ньому писатиметься код.

#### P3 — ADC батареї, двоточкове калібрування

**Залізо:** лабораторний блок на J1 замість акумулятора.
**Прошивка:** `esp_adc` oneshot + curve-fitting, друк кожну секунду: сире значення, мВ після калібрування, VBAT після множення на 4.033.
**Процедура:** виставити 8.4 В, записати пару (вольтметр на TP1 / друковане VBAT); виставити 6.5 В, записати другу пару. Порахувати поправку.
**Що вирішує:** справжній масштаб ADC. Коефіцієнт дільника вже виміряний (4.033), але власна похибка ADC ±2–3 % більша за похибку резисторів, і тільки двоточковий замір її знімає.
**Приймання:** після поправки друковане VBAT збігається з вольтметром у межах **±50 мВ** в усьому діапазоні 6.0–8.4 В.
**Заповнює:** `VBAT_SCALE` і `VBAT_OFFSET` у NVS; підтверджує `VBAT_CUTOFF_MV`.

#### P4 — далекоміри і перепризначення адрес

**Залізо:** + U7…U10 на шлейфах. Вимагає пройденої P1.
**Прошивка:** мінімальний драйвер VL53L0X (варіант 3 із 10.3) + послідовність XSHUT із 4.7.
**Порядок:** спершу під'єднати **один** далекомір, переконатись, що видно 0x29 і що він повертає відстань. Потім додати решту по одному. Лише після цього пробувати повну послідовність із перепризначенням на 0x30–0x33.
**Що вирішує:** чи працює вибраний драйвер (конфлікт 10.3) і чи справді ~100 мкА підтяжки PCF8574 достатньо, щоб підняти XSHUT (4.4 — це теоретичний ризик, який перевіряється тільки тут).
**Приймання:** чотири пристрої на 0x30, 0x31, 0x32, 0x33; кожен дає правдоподібну відстань до долоні й до стіни; після перезавантаження послідовність відтворюється стабільно 10 разів підряд.
**Заповнює:** `TOF_OBSTACLE_MM` (експериментально на шасі), підтверджує 10.3.

#### P5 — приймання CRSF

**Залізо:** + приймач у J7, привʼязаний до TX12.
**Прошивка:** UART2 на 420000 8N1, читання байтів, збирання кадрів, друк: тип кадру, довжина, лічильники «CRC ok / CRC fail», і всі 16 розпакованих каналів у форматі мкс.
**Що вирішує:** `CRSF_BAUD` (конфлікт 10.2) і **справжню карту каналів**. Розділ 1.3 каже «1 = поворот, 2 = тяга, 5 = ARM, 6 = фари», але це налаштування пульта, а не властивість протоколу — перевіряється тільким тим, що ти рухаєш стік і дивишся, який індекс змінився.
**Приймання:** частка `CRC fail` менша за 1 %; кожен названий у 1.3 орган керування монотонно змінює рівно один канал у діапазоні 172…1811; при вимкненні пульта кадри припиняються (це і є майбутній failsafe).
**Заповнює:** `CRSF_BAUD`, підтверджує або виправляє карту каналів у 1.3.

#### P6 — енкодери, обертання рукою

**Залізо:** + мотори на шлейфах. **Вимагає пройденої прозвонки шлейфів** (розділ 4 документа `01-ASSEMBLY-BRINGUP.md`) — це блокер, не рекомендація.
**Прошивка:** чотири юніти PCNT у квадратурному режимі (шаблон 8.2), фільтр 1000 нс, друк чотирьох лічильників двічі на секунду. Два прогони: з `gpio_pullup_en()` і без.
**Процедура:** колесо в повітрі, повернути рукою рівно 10 обертів, зчитати приріст, поділити на 10. Повторити тричі й узяти середнє.
**Що вирішує:** `ENC_PULSES_PER_REV`, `ENC_NEEDS_PULLUP` (якщо без підтяжок лічильник стоїть, а з ними рахує — вихід відкритий колектор), і яке фізичне колесо відповідає якому роз'єму M1–M4.
**Приймання:** усі чотири канали рахують; три прогони по 10 обертів дають розбіжність менше 2 %; обертання в різні боки дає приріст різного знаку.
**Заповнює:** `ENC_PULSES_PER_REV`, `ENC_NEEDS_PULLUP`.

#### P7 — мотори на мінімальному ШІМ і знак енкодера

**Залізо:** усе. **Колеса в повітрі, шасі на підставці.**
**Прошивка:** LEDC 20 кГц, STBY вгору, по консольній команді подати **25 %** ШІМ на один борт на 2 секунди, друкуючи приріст лічильників. Жодного мікшера, жодного PID — тільки «подати на борт N напрямок D».
**Що вирішує:** `ENC_DIR_SIGN[4]` і перевірку прив'язки з 2.2 (`U5`: AO1/AO2 → **M4**, BO1/BO2 → **M3** — ця перехресна прив'язка легко плутається).
**Приймання:** команда «лівий борт вперед» крутить обидва ліві колеса вперед і обидва лічильники в один бік; те саме для правого; жодне колесо не крутиться в протилежний бік.
**Заповнює:** `ENC_DIR_SIGN[4]`, підтверджує 2.2.

**P7 — викидний зонд, а не фаза 1.** Фаза 1 будує ту саму функціональність заново, але з arm/disarm, failsafe, мікшером і відсічкою по напрузі. Тут усе це свідомо відсутнє, бо завдання P7 — зняти знаки, а не поїхати.

#### Що не вимірюється прошивкою

`WHEEL_DIAMETER_MM` і `WHEEL_BASE_MM` — штангенциркуль і лінійка по шасі. `MOTOR_MAX_PWM` лишається 0.75 до фази 5. Внести в `docs/measured.md` разом з рештою.

### 7.0.1 Методологія: SDD для фаз, вимірювання для передфаз

Робота над прошивкою ведеться по **SDD (spec-driven development)**: для кожної фази спершу пишеться специфікація, потім план, потім задачі, і лише потім код. Нижче — що це означає конкретно для цього проєкту.

**Специфікація фази містить:**

1. **Обсяг** — які пункти розділу 5 ця фаза закриває, і чого вона свідомо не робить.
2. **Вхідні константи** — перелік величин із розділу 9, на які фаза опирається, з їхніми **фактичними** значеннями й посиланням на передфазу, що їх дала.
3. **Критерії приймання** — у форматі «дано / коли / тоді». Для фаз 0–7 вони вже сформульовані в розділі 7; специфікація їх уточнює до перевірюваних, а не переписує.
4. **Апаратні передумови** — що має бути під'єднано, і що свідомо **не** під'єднано (колеса в повітрі, мотори від'єднані тощо).
5. **Поведінка при відмові** — що робить підсистема, коли її залізо не відповідає. Для цього проєкту це не формальність: STBY і failsafe важливіші за будь-яку функцію.

**Головне правило, і воно специфічне саме для цього проєкту:**

> **Специфікація фази не пишеться, доки її вхідні константи — «?».**

Це найімовірніший спосіб зіпсувати тут SDD. Специфікація виглядає тим переконливішою, чим вона конкретніша, тому агент під тиском «напиши специфікацію» схильний підставити правдоподібне число замість «?» — і далі вся низхідна ланцюжок план → задачі → код буде коректною реалізацією неправильного припущення, причому помилка виявиться аж на залізі. Передфази P0–P7 існують саме для того, щоб цього не сталося: вони перетворюють припущення на заміри **до** появи специфікації.

Якщо константа потрібна, а передфаза ще не пройдена — правильна дія не «взяти типове значення», а **зупинитись і сказати, якого заміру не вистачає**.

**Передфази SDD не підлягають.** У них немає специфікації, плану й задач; у них є мета заміру, процедура і критерій приймання. Писати спеку на 80 рядків коду, який виведе в консоль одне число й буде видалений, — це витрачений цикл.

**Що є артефактом, а що ні:**

| Артефакт | Хто створює | Куди йде |
|---|---|---|
| `docs/measured.md` | передфази P0–P7 | джерело для розділу 9 і `calib.h` |
| Специфікація фази | SDD, перед кодом | репозиторій, `docs/features/<slug>/spec.md` |
| План і задачі фази | SDD, після спеки | репозиторій |
| Код фази | після плану | `components/`, `main/` |
| Журнал bring-up | `01-ASSEMBLY-BRINGUP.md`, розділ 7 | README і захист |

**Де цей документ у схемі SDD.** Він не є специфікацією — він **джерело вимог**. Розділи 1–4 — незмінні обмеження заліза, які будь-яка специфікація мусить дотримати. Розділ 5 — обсяг. Розділ 9 — явний перелік того, чого ми ще не знаємо. Специфікації фаз пишуться **на основі** цього документа і живуть окремо від нього.

### 7.0.2 Порядок розгортання репозиторію і підключення SDD

Порядок має значення: кілька кроків робить **людина, а не агент**, і робить їх до того, як агент узагалі отримає доступ до репозиторію.

**Крок 1. ESP-IDF і порожній проєкт — вручну, через розширення VS Code.**

Скелет ESP-IDF створює розширення (`ESP-IDF: New Project`, ціль `esp32s3`), а не агент. Причина не в недовірі: розширення разом із проєктом генерує `.vscode/settings.json` і `c_cpp_properties.json` із правильними шляхами включень і `compile_commands.json`. Якщо `CMakeLists.txt` напише агент від руки, збірка може працювати, а IntelliSense — ні, і вечір піде на червоні підкреслення, за якими немає помилок.

Зібрати, прошити й відкрити монітор на **порожньому** проєкті. Це водночас і є передфаза **P0**: якщо порожній проєкт не прошивається, проблема в установці, і це видно до того, як у грі зʼявився агент.

**Крок 2. `git init` і коміт порожнього скелета.** Baseline до першого рядка агента. Далі будь-яку його зміну видно в діффі.

**Крок 3. Покласти обидва документи в `docs/`** — `01-ASSEMBLY-BRINGUP.md` і цей файл. Вони мають бути в репозиторії, а не лише в чаті: стадії SDD перечитують вхідні файли з диска.

**Крок 4. Тільки тепер підключати SDD.**

**Крок 5. Для входу використати `survey`, а не `scaffold`.** `scaffold` призначений для порожнього репозиторію і спробує накинути власну структуру; у нас скелет ESP-IDF уже є й він канонічний. `survey` навпаки — читає те, що є, і фіксує як даність.

**Крок 6. Конституція — до першої специфікації.** Її читає кожна наступна стадія, тому це найвища за важелем дія у всьому налаштуванні. Готовий текст — нижче.

**Крок 7. Передфази P1–P7 — поза циклом SDD** (див. 7.0). Для них не запускаються `specify`/`plan`/`tasks`.

**Крок 8. Далі по одній фазі = по одній «фічі»** зі своїм слагом: `phase0-skeleton`, `phase1-drive`, `phase2-io`, `phase3-crsf` і так далі. Не одна велетенська специфікація на всю прошивку.

#### Де живуть діагностичні прошивки

Один проєкт `tools/bringup/` з перемикачем на початку `main.c`:

```c
#define BRINGUP_TEST 1   // 0=chip/psram 1=i2c scan 2=pcf 3=adc
                         // 4=tof 5=crsf 6=encoders 7=motors
```

Перемикання тесту — зміна числа, `idf.py flash monitor`, тридцять секунд. Вісім окремих проєктів давали б вісім `set-target` і вісім повних збірок на порожньому місці.

#### Проєкт конституції

Текст нижче можна віддавати як є. Він складається з речей, які **не підлягають обговоренню агентом** ні на якій стадії:

```
1. Джерело істини про залізо — kicad-rover.net. Якщо документ і нетліст
   розходяться, правий нетліст, і про розходження треба сказати вголос.

2. Номери GPIO існують рівно в одному файлі: components/board/board_pins.h.
   Літерал номера піна будь-де ще — дефект, навіть якщо значення правильне.

3. Величини з розділу 9 документа 02-FIRMWARE-CONTEXT.md не вигадуються.

   і назвати, якого заміру бракує. Підставити "типове значення" заборонено.

4. Специфікація фази не пишеться, доки її вхідні константи невідомі.

5. ESP-IDF v6.1, тільки нові драйвери: esp_adc, gptimer, pulse_cnt,

7. Інваріанти безпеки, сильніші за будь-яку функціональність:

   - перша операція по I²C після старту — запис 0x00 у PCF8574;
   - ШІМ обмежений 0.75 до завершення фази 5;
   - VBAT < 6.0 В → мотори не запускаються.

8. Будь-яка задача вважається завершеною лише якщо idf.py build
```

#### Де TDD-рушій буде опиратися

SDD-плагін побудований навколо циклу «спершу червоний тест». Для лівої колонки таблиці 6.4 це працює ідеально. Для правої — ні, і це треба вирішити **до** першої фази, а не в процесі.

Рішення просте: для HAL-задач критерій приймання — **фізична перевірка**, записана в журнал bring-up, а не автотест. Конституція це вже закріплює пунктом 6.

Чого не можна допустити: щоб агент, не маючи способу написати справжній тест, написав тест на мок — «перевірити, що `ledc_set_duty()` викликано з duty=768». Такий тест зелений завжди, не ловить жодної апаратної несправності, і створює хибне відчуття покриття. Краще чесний запис «перевірено на залізі 16.10, обидва борти крутяться вперед», ніж зелена галочка ні про що.

Команди збірки й тестів задаються явно, бо автовизначення на ESP-IDF-репозиторії корисного не знайде: збірка — `idf.py build`, тести — запуск хостового раннера з `test/host/`.

### Фаза 0 — скелет
**Залізо:** тільки ESP32 (можна навіть не на платі).
**Робимо:** структура проєкту, `board_pins.h`, збірка, прошивка через USB, консоль, логування, NVS, Task WDT, порожня машина станів із логом переходів.
**Приймання:** прошивається, консоль відповідає, `esp_task_wdt` зареєстрований, стан друкується.

### Фаза 1 — живлення і мотори
**Залізо:** U1, U2, U3, U4, U5. **Колеса в повітрі.**
**Робимо:**
- LEDC 20 кГц, 10 біт, два канали;
- GPIO DIR ×4, STBY;
- `drive_set(left, right)` зі значеннями −1.0…+1.0;
- мікшер танкового приводу: `left = throttle + steer`, `right = throttle − steer`, з нормалізацією при переповненні;
- **arm/disarm і таймер failsafe уже тут** — поки без CRSF, по консольній команді;
- ADC батареї, відсічка при < 6.0 В.

**Чому arm/disarm саме тут, а не пізніше:** мотори — єдина підсистема, здатна втекти зі столу. Шлях «зупинити» має існувати раніше, ніж шлях «поїхати».

**Приймання:** консольна команда `drive 0.3 0` крутить обидва борти вперед; `disarm` зупиняє; відʼєднання USB не викликає руху; при VBAT < 6.0 В мотори не запускаються.

**Обмеж ШІМ на рівні 0.75** до завершення фази 5 — мотори JGA12-N20 на 8.4 В крутяться вище номіналу.

### Фаза 2 — I²C, PCF8574, світло, зумер
**Залізо:** + U6.
**Робимо:**
- новий драйвер `i2c_master`, 100 кГц, мʼютекс;
- скан шини при старті, лог знайдених адрес;
- **перша операція — запис `0x00`**;
- тіньовий регістр PCF8574 (read-modify-write у памʼяті, не з шини);
- API `ioexp_set_bit(bit, val)`;
- фари, стоп-сигнали червоний/зелений;
- зумер через LEDC, окремий таймер, функція `beep(freq, ms)` неблокуюча.

**Приймання:** при подачі живлення світло **не загоряється** (бо 0x00 записано першим); консольні команди вмикають кожен канал окремо; зумер пищить на заданій частоті.

### Фаза 3 — ELRS / CRSF
**Залізо:** + приймач у J7, привʼязаний до пульта.
**Робимо:**
- UART2, **420000 8N1**, RX=GPIO17, TX=GPIO16;
- `uart_driver_install` з чергою подій;
- парсер кадрів: `[0xC8][len][type][payload][crc8]`;
- CRC8 поліном **0xD5** по `type+payload`;
- тип `0x16` RC_CHANNELS_PACKED: 22 байти, 16 каналів по 11 біт;
- перетворення: `us = (val − 992) × 5 / 8 + 1500` (172→988, 992→1500, 1811→2012);
- таймер failsafe: немає валідного кадру **500 мс** → FAILSAFE;
- відкидання кадрів із битим CRC і неправильною довжиною **без** скидання таймера.

**Приймання:** стіки пульта рухають мотори; вимкнення пульта → зупинка за 500 мс + зумер; навмисне подання сміття в UART не ламає стан.

### Фаза 4 — енкодери
**Залізо:** + мотори з перевіреною розпіновкою шлейфів.
**Робимо:**
- 4 юніти PCNT у квадратурному режимі;
- glitch-фільтр 1000 нс;
- внутрішні підтяжки, **якщо** вимір показав відкритий колектор;
- watch-point на межах ±30000 з callback, що акумулює в `int64` — **так обробляється переповнення 16-бітного лічильника**;
- обчислення швидкості: різниця лічильника за фіксований інтервал GPTimer;
- калібрувальні константи з розділу 9.

**Приймання:** прокрутка колеса рукою на 10 обертів дає стабільне число; знак збігається з напрямом; на максимальному ШІМ лічильник не зривається.

### Фаза 5 — PID
**Робимо:**
- PID по швидкості на кожен борт;
- **saturation виходу** та **anti-windup** (clamping інтегратора);
- коефіцієнти в NVS, консольні команди `pid kp 1.2`;
- плавний розгін (ramp) на вході завдання.

**Приймання:** борт тримає задану швидкість при зміні навантаження (притискання колеса пальцем); інтегратор не розганяється при заблокованому колесі; зміна коефіцієнта з консолі діє одразу.

### Фаза 6 — далекоміри й протизіткнення
**Залізо:** + 4× VL53L0X.
**Робимо:**
- послідовність XSHUT і перепризначення адрес (розділ 4.7);
- безперервний режим вимірювання;
- медіанний фільтр 3–5 відліків, відсів `out of range`;
- логіка: перешкода ближче порогу в напрямку руху → обмеження швидкості в цьому напрямку до 0, рух у протилежний бік дозволений;
- **деградація:** відмова одного сенсора не валить систему, лог + відповідний сектор вважається вільним і пишеться попередження.

**Приймання:** ровер зупиняється перед перешкодою і дозволяє здати назад; виймання одного сенсора на ходу не вішає прошивку.

### Фаза 7 — телеметрія, інтеграція, документація
**Робимо:**
- CRSF-телеметрія назад на пульт (напруга батареї — тип `0x08` Battery Sensor);
- вимір часу такту керування через `esp_timer_get_time()`, вивід у телеметрію;
- README, блок-схема, інструкція запуску, опис інтерфейсів;
- заповнений чекліст самоперевірки.

| LEDC | `driver/ledc.h` | — |
| UART | `driver/uart.h` | — |

**ESP-IDF v6.0 видалив legacy-драйвери остаточно** — `driver/adc.h`, `driver/timer.h` і `driver/pcnt.h` більше не існують. `driver/i2c.h` оголошений End-of-Life у v6.0 і буде видалений у v7.0. Тобто вибір вище зараз не рекомендація, а єдиний робочий варіант.

Дві дрібні зміни v6.0, на яких легко спіткнутися в коді CRSF і ШІМ:

- `UART_FIFO_LEN` видалено → використовувати **`UART_HW_FIFO_LEN`**
- `soc/uart_channel.h` видалено → **`soc/uart_pins.h`**
- `ledc_timer_set()` видалено → `ledc_timer_config()` або `ledc_set_freq()`

### 8.2 Квадратурний PCNT — робочий шаблон

```c
pcnt_unit_config_t unit_cfg = {
    .high_limit =  30000,
    .low_limit  = -30000,
    .flags.accum_count = true,   // акумулювати при досягненні межі
};
pcnt_new_unit(&unit_cfg, &unit);

pcnt_glitch_filter_config_t filter = { .max_glitch_ns = 1000 };
pcnt_unit_set_glitch_filter(unit, &filter);

// канал A: рахує по фронтах A, напрям визначає рівень B
pcnt_chan_config_t cfg_a = { .edge_gpio_num = PIN_A, .level_gpio_num = PIN_B };
pcnt_new_channel(unit, &cfg_a, &chan_a);
pcnt_channel_set_edge_action(chan_a, PCNT_CHANNEL_EDGE_ACTION_DECREASE,
                                     PCNT_CHANNEL_EDGE_ACTION_INCREASE);
pcnt_channel_set_level_action(chan_a, PCNT_CHANNEL_LEVEL_ACTION_KEEP,
                                      PCNT_CHANNEL_LEVEL_ACTION_INVERSE);

// канал B: дзеркально — це дає ×4 роздільність
pcnt_chan_config_t cfg_b = { .edge_gpio_num = PIN_B, .level_gpio_num = PIN_A };
// ... дзеркальні дії

pcnt_unit_add_watch_point(unit, 30000);
pcnt_unit_add_watch_point(unit, -30000);
pcnt_unit_register_event_callbacks(unit, &cbs, ctx);  // переривання + переповнення
```

### 8.3 ADC з калібруванням

```c
adc_oneshot_unit_init_cfg_t init = { .unit_id = ADC_UNIT_1 };
adc_oneshot_chan_cfg_t chan = {
    .bitwidth = ADC_BITWIDTH_DEFAULT,
    .atten    = ADC_ATTEN_DB_12,        // 0..3100 мВ
};
adc_oneshot_config_channel(h, ADC_CHANNEL_0, &chan);   // ADC_CHANNEL_0 = GPIO1

// на S3 доступна схема curve fitting
adc_cali_curve_fitting_config_t cali = {
    .unit_id = ADC_UNIT_1, .atten = ADC_ATTEN_DB_12,
    .bitwidth = ADC_BITWIDTH_DEFAULT,
};
adc_cali_create_scheme_curve_fitting(&cali, &cali_h);

// mV -> VBAT
int vbat_mv = v_adc_mv * 4033 / 1000;   // k=4.033, виміряно на платі (розрахункове 4.0303)
```

Коефіцієнт тримати в NVS, а не в коді, і давати можливість перекалібрувати однією командою в консолі: оператор міряє реальний VBAT вольтметром, вводить його, прошивка ділить на поточне сире значення ADC і зберігає новий `k`. Це знімає похибку ADC, яка тут більша за похибку резисторів.

### 8.5 Пастки, на яких легко втратити вечір

| Пастка | Наслідок | Що робити |
|---|---|---|
| Не записати 0x00 у PCF8574 першим | світло горить із моменту ввімкнення, I²C-конфлікт чотирьох ToF | перша транзакція після init |
| Хардкод адреси PCF8574 | не знаходить пристрій | взяти з результату скану (розділ 10.1) |
| Один VL53L0X ініціалізований без утримання решти в reset | усі на 0x29, шина не працює | строго послідовність 4.7 |
| 400 кГц на I²C | випадкові NACK на довгих шлейфах | 100 кГц |
| Забути glitch-фільтр PCNT | лічильник «набігає» при роботі моторів | 1000 нс |
| STBY не опущений у FAILSAFE | мотори продовжують крутитись при втраті звʼязку | опускати в кожному небезпечному стані |
| Скидання failsafe-таймера на битому кадрі | звʼязок «живий» при повному шумі | таймер скидає тільки кадр, що пройшов CRC |
| `vTaskDelay` замість `vTaskDelayUntil` | дрейф періоду керування, нерівний PID | `vTaskDelayUntil` у всіх періодичних задачах |
| ШІМ на повну при першому пуску | мотори на 8.4 В крутяться вище номіналу | обмеження 0.75 до калібрування |

## 10. Відкриті конфлікти — вирішити до написання коду

### 10.1 Адреса PCF8574 — діапазон звужено, точне значення ще ні

**Чіп ідентифіковано візуально: PCF8574T** (15.10.2026). Це базовий варіант, не «A», тому діапазон адрес — **тільки `0x20…0x27`**, а `0x38…0x3F` виключені остаточно. Шукати їх не треба.

У схемі записано `addr 0x20 (A0..A2=GND)`, але фізичні модулі цього типу часто приходять з A0–A2 підтягнутими **вгору**, що дає `0x27`. Яке з восьми — визначає передфаза **P1**.

Умови для чистого заміру вже є: R17/R19 не встановлені, підтяжки дає сам модуль PCF8574 (див. 4.6), далекоміри підключаються шлейфами й на час скану від'єднані. Отже на шині буде **рівно один пристрій**, і скан дасть однозначну відповідь без конфлікту з чотирма 0x29.

**Рішення:** все одно не хардкодити. Прошивка сканує `0x20…0x27` при старті й логує знайдене; якщо знайдено не рівно один — це помилка самоперевірки, а не повод вгадувати.

### 10.2 Швидкість CRSF: 416666 чи 420000

Опис символу J7 у схемі каже `CRSF over UART 416666 baud`. Стандарт CRSF і всі ELRS-приймачі працюють на **420000**. Число 416666 трапляється в старішій апаратурі TBS.

**Рішення:** базово 420000. Якщо приймач не відповідає — спробувати 416666. ESP32 відтворює 420000 із похибкою ~0.25 %, це в межах допуску UART.

### 10.3 Драйвер VL53L0X

Офіційного компонента в ESP-IDF немає. Варіанти:

1. портувати офіційний ST VL53L0X API (великий, але перевірений);
2. взяти компонент зі спільноти;
3. написати мінімальний драйвер самостійно — для задачі потрібні лише `init`, `setAddress`, `startContinuous`, `readRangeMillimeters`.

**Рекомендація — варіант 3.** Повний API ST тягне тисячі рядків заради калібрувань, які тут не потрібні, і його складно адаптувати під новий `i2c_master`. Мінімальний драйвер на ~300 рядків дає все потрібне, і на захисті його можна пояснити.

### 10.4 Розпіновка моторного шлейфу — не підтверджена

**Це блокер для фази 1.** Доки не прозвонено (розділ 4 документа `01-ASSEMBLY-BRINGUP.md`), мотори не під'єднувати. Якщо порядок дротів відрізняється від схеми, вихід драйвера потрапить на `+3V3_PERIPH`.

### 10.5 Тип виходу енкодера — не підтверджений

Якщо відкритий колектор — потрібні `gpio_pullup_en()` на всіх восьми лініях. Якщо енкодер вимагає 5 В — це переробка плати, і фази 4–5 треба переглядати.

## 11. Що ще передати агенту разом із цим документом

Обовʼязково:

1. **`kicad-rover.net`** — найвища інстанція при будь-якому сумніві щодо пінів
2. **`01-ASSEMBLY-BRINGUP.md`** — щоб агент розумів, яке залізо доступне на кожній фазі
3. **`docs/measured.md`** — результати передфаз P0–P7. Поки його немає, агент може писати лише самі передфази, а не специфікації фаз (див. 7.0.1)

**Перше завдання агенту — не специфікація, а передфази.** Якщо передати йому цей документ і сказати «почни по SDD», він за визначенням почне зі спеки фази 0, бо так виглядає методологія. Правильний старт — попросити діагностичні прошивки P0–P2, зняти числа, і лише тоді переходити до SDD-циклу. Інакше перша ж специфікація буде написана на вигаданій адресі PCF8574.

Бажано:

4. `bom-kicad-rover.csv` — номінали для пояснення розрахунків у README
5. Фото зібраної плати зверху і знизу — для README і презентації
6. Паспорт моторів JGA12-N20, якщо знайдеться (напруга, струм стопора, передавальне число)

Не потрібно: `.kicad_sch`, `.kicad_pcb`, `.kicad_sym` — уся інформація, релевантна прошивці, уже витягнута в розділи 2–4.
