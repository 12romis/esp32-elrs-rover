# 0002 — Accumulate counts by modular difference in encoders core

- **Status:** Accepted
- **Date:** 2026-10-19
- **Deciders:** Розробник проєкту, Агент (design, рівень easy)

## Context

Апаратний лічильник імпульсів ESP32-S3 16-бітний; на заданій межі він скидається в нуль, якщо ввімкнені порівнювачі меж (драйвер вмикає їх, коли на межі стоїть watch-point; P6 працював саме так). Spec §6 вимагає накопичення без переповнення щонайменше 10^15 імпульсів у кожен бік і 0 стрибків під час переходу через межу (AC-04). Вбудоване накопичення драйвера (`accum_count` з watch-point на межах) віддає значення в 32-бітному `int`, тобто ≈ 2.1 · 10^9 імпульсів — менше за вимогу. Документ 02 §8.2 пропонує watch-point на ±30000 і callback, що накопичує в `int64`. Вибірку робить окрема задача кожні 20 мс (ADR-0001).

## Decision drivers

- Spec §6: ≥ 10^15 імпульсів без переповнення; 0 стрибків і 0 змін знака на ≥ 100 000 імпульсів (AC-04).
- Конституція, п. 6: логіка в core з тестами на хості; HAL не тестується на моках.
- Відсутність гонки між накопичувачем і апаратним лічильником, яка дала б стрибок на ±30000.

## Considered options

1. **Різниця за модулем у core** — блок лічильника працює з межами ±30000 без `accum_count`, з watch-point на ±30000 без callback (лише щоб увімкнути порівнювачі меж, як у P6); на межі він скидається в нуль, тож сирі значення узгоджені за модулем 30000. На кожній вибірці `encoders_core` зводить різницю нового й попереднього сирого значення до (−15000, 15000], множить на знак колеса й додає до `int64_t` накопичувача.
2. **Watch-point і накопичення в перериванні (документ 02 §8.2)** — callback на ±30000 додає межу до власного `int64_t`; показ = накопичувач + сире значення. Не залежить від частоти вибірок, але читання накопичувача й сирого значення мусить бути атомарним відносно переривання, інакше на межі виникає стрибок на ±30000 — саме той, що забороняє AC-04; ця логіка живе в HAL і хостовими тестами не покривається.
3. **Вбудоване накопичення драйвера в `int`** (виключено обмеженням spec §6, наведено для повноти) — найпростіше, але 2.1 · 10^9 імпульсів не задовольняють вимогу spec §6, а розширити тип драйвера не можна.

## Decision outcome

**Chosen:** варіант 1. Уся логіка переходу через межу стає чистою функцією з вичерпними тестами на хості (перехід вгору й вниз, багаторазовий, з одночасним рухом, граничні значення накопичувача), без переривань і без спільного стану з ISR. 64-бітний накопичувач дає ≈ 9.2 · 10^18 — з великим запасом понад 10^15.

## Consequences

**Positive**
- Немає переривань і гонок; перехід через межу перевіряється на хості.
- Знак колеса застосовується до приросту в одному місці, перед накопиченням.
- Той самий крок дає й приріст для швидкості — одне джерело правди.

**Negative**
- Умова коректності: між двома вибірками колесо проходить менше 15000 імпульсів. За верхньої межі spec §6 (20 000 імпульсів/с) це ≈ 0.75 с без жодної вибірки — вже зависання задачі; пропуск понад 0.75 с задача пише в журнал, повне зависання ловить Task WDT (5 с).
- Спирається на поведінку заліза «з увімкненими порівнювачами меж лічильник скидається в нуль»: хостом не перевіряється, лише приймання AC-04 на залізі (SAD §11).
- Відхід від документа 02 §8.2; документ оновлюється лише за вказівкою Розробника.

**Neutral**
- Якщо приймання AC-04 покаже стрибки, HAL можна перевести на варіант 2, не змінюючи інтерфейс знімка.
