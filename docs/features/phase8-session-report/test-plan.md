# Test plan — phase8-session-report

Фаза має: вимкнути й увімкнути захист далекомірами з пульта (CH9) із зеленим індикатором, назвати в консолі всі датчики перешкоди та надсилати після роззброєння звіт сесії, не втрачаючи двох останніх (spec §2). Тестів ще немає: цей план пишеться до них, `implement` пише червоні тести за ним.

## Levels

| Level | Scope | Strategy (generic — no tool names) |
|---|---|---|
| Unit | Чиста логіка в `*_core.c` без заголовків ESP-IDF: режим CH9, зайнятість секторів, межі сесії, статистика, документ, пакети, черга, форматування консолі, колір індикатора. | У памʼяті на Розробнику (хостовий прогін, п. 6 конституції), без заліза й мережі. |
| Integration | Прошивка на платі проти реальної залежності, якою володіє модуль: брокер, Wi-Fi, сховище. | Ефемерний реальний брокер на машині Розробника з тестовим сертифікатом і тестовим коренем довіри; також перезапуск плати для сховища. |
| Contract | Межа між двома учасниками: байти пакетів, формат документа, рядки консолі, канал пульта, колір індикатора. | Перевірка реальних байтів і рядків проти `contracts/events.md` і `contracts/cli.md`, без рукописних заглушок. |
| E2E | Один наскрізний потік на історію: крок приймання на залізі (виконує Розробник). | Потік через справжні входи: пульт, консоль, плата, мережа. |
| Load | Числові NFR із spec §6. | Багаторазові прогони замірів на платі з журналом (повтор, межі, поріг), див. розділ нижче. |
| Component / Visual-regression / E2E-through-UI | <!-- N/A: UI-поверхні немає (`target_surfaces: [cli]`) --> | — |

## Edge cases / error paths

- AC-04: значення каналу рівно посередині (992) → «вимкнено», прошивка не вгадує призначення тумблера → expected: захист вимкнений, `status` показує режим (OQ-6).
- AC-02/AC-03: перемикач дребезжить між кадрами → expected: одна подія на зміну, безпека не залежить від кількості подій.
- AC-07: знімок далекомірів застарів під час руху → expected: «не охороняє», зелений гасне, одне попередження.
- AC-09: два з трьох передніх датчиків у відмові → expected: названий лише третій справний, якщо він нижче порога; інакше рядок без датчиків не з'являється.
- AC-08: зайняті обидва сектори → expected: датчики обох секторів, кожен з позначкою.
- AC-10: сервер відповідає відмовою на з'єднання → expected: результат «відмова сервера», публікація не відправляється.
- AC-10: підтвердження приходить з чужим номером пакета → expected: не вважається підтвердженням, звіт лишається.
- AC-11: усі дані відсутні → expected: документ валідний, усі відповідні поля порожні значення.
- AC-13: метадані втрачені, слоти цілі → expected: номер сесії відновлено з найбільшого слота плюс одиниця.
- AC-13: слот пошкоджений → expected: ігнорується, решта черги працює.
- AC-14: мережі немає, сервер мовчить, сертифікат недовірений, відмова → expected: для кожного окрема причина в журналі, одне повідомлення на спробу.
- AC-15: третя сесія при двох невідправлених → expected: найстарший видалено з номером у журналі.
- AC-16: перший звіт не підтверджено → expected: спроба зупинена, другий не надсилається, порядок у черзі збережено.
- AC-17: команда `report` з аргументом → expected: «зайві аргументи», нічого не змінюється.
- AC-18: озброєння збіглося із записом у памʼять плати → expected: озброєння й крок керування можуть затриматись на тривалість запису (виняток NFR), тривалість заміряно.
- AC-19: черга підсумків між керуванням і мережею повна → expected: найстарший затирається, керування не чекає.
- AC-20: розворот на місці, штовхання вручну → expected: пробіг не росте.
- AC-21: жодного доступного енкодера борту → expected: швидкості борту й дисбаланс порожні.
- AC-22: недовірений сертифікат при двох звітах у черзі → expected: жоден не відправлено, порядок і кількість у черзі незмінні.
- AC-23: збірка без файлу налаштувань → expected: збірка проходить, передача вимкнена (AC-24).
- AC-24: `report` у DISARMED без файлу налаштувань → expected: «налаштування мережі не задано», без падіння.

## Test data

- Seed strategy: фабрики підсумків сесії в хостових тестах (набори входів кроку: пряма їзда метр, розворот, штовхання, недоступний борт, кілька утримань); еталонні байти пакетів зі стандарту; два JSON-приклади з `contracts/events.md` як контрактні фікстури; тестовий сертифікат і тестовий корінь довіри для ефемерного брокера; тестовий файл налаштувань мережі лише локально.
- Integration dependency: ефемерний реальний брокер (одноразовий, на машині Розробника), не заглушка; за потреби — реальний сервер власника при прийманні.
- Cleanup boundary: per-suite для брокера (запуск і зупинка навколо серії); per-test для памʼяті плати: перед кожним сценарієм черга порожня (команда стану й очищення черги в тестовій збірці, або чисте стирання розділу сховища); перезапуск плати між сценаріями AC-13.

## NFR validation (load)

- Вплив на керування: 0 нових кроків довших за період 20 мс під час спроби → 30 послідовних спроб передачі з відкритим `status`, перед кожною й після кожної записати рядок часу кроку; допустимі лише збіги з моментами запису в памʼять плати.
- Тривалість спроби ≤ 30 с → 30 послідовних спроб (10 успішних, 10 без мережі, 10 з недовіреним сертифікатом) із мітками журналу; очікується ≤ 30 с у кожній.
- Вільна внутрішня памʼять після вимкнення Wi-Fi не менша за значення до спроби мінус 4096 байт; поріг ≥ 345000 байт зберігається → 30 спроб поспіль, значення до й після кожної; жодного дрейфу вниз понад межу.
- Реакція індикації ≤ 200 мс → 20 перемикань CH9 із записом відео або міток; найгірше значення ≤ 200 мс.
- Точність пробігу ±5 % на 1 м → 10 проїздів по рулетці; усі в межах.
- Розмір звіту ≤ 1024 байти → хостовий прогін на найгіршому наборі полів (найдовші рядки, усі числа максимальні).
- Записи в памʼять плати ≤ 2 на сесію → 10 сесій із лічильником записів; не більше двох на сесію.

## CI placement

- On every PR: unit і contract (хостові тести `run_tests` і перевірки гігієни секретів, ядер без заголовків IDF, захищених файлів).
- On schedule / pre-release: integration (ефемерний брокер, перезапуск плати), e2e і load на залізі — виконує Розробник за `acceptance.md` (T17) перед злиттям.
