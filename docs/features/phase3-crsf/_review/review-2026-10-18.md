## Findings

### F1 — [stage-2] Без підписки `control` на Task WDT пульт однаково озброює ровер і крутить мотори

- **Де:** `components/drive/drive_hal.c:249-255`, `:278-280`; AC-01, AC-03 (ADR-0004 фази 1).
- **Суть:** коли `esp_task_wdt_add` повертає помилку, код лише не ставить `s_running`, а його перевіряє тільки `drive_hal_submit`, тобто консоль. Цикл `control` далі викликає `drive_ctl_step` і `apply_outputs`. Тож фронт тумблера дає ARMED, а стік дає ШІМ і STBY без сторожового таймера. Коментар у рядку 251 («arm і drive недоступні») з фази 3 не відповідає дійсності.
- **Пропозиція:** при `err != ESP_OK` тримати виходи вимкненими й не виконувати запитів ARMED (наприклад, подавати в крок знімок без кадрів).
- **Verdict:** Fix now.

### F2 — [stage-1] Відмова за станом у FAILSAFE завжди каже «лише апаратним скиданням», навіть коли причина — втрата зв'язку

- **Де:** `components/rover_console/console_core.c:295-297` (так само `:491-493` для `light`/`beep`); `main/main.c:104-117`; AC-08, AC-09; `contracts/cli.md:19` (клас 1).
- **Суть:** контракт вимагає сказати, що вихід можливий апаратним скиданням **або, після втрати зв'язку, пультом**. Для FAILSAFE з причиною «втрата зв'язку» команди `arm`, `drive`, `reboot`, `wdt-test`, `light`, `beep` дають хибне пояснення, яке суперечить AC-08 і відповіді `disarm`. До того ж `status` не показує, чого бракує для виходу: `s_status.fsx` рахується (`drive_hal.c:308`), але в `rc_status` не використовується.
- **Пропозиція:** передавати причину FAILSAFE у `console_fmt_denied` / `console_fmt_ui_denied`, додати в `crsf_fmt_status` рядок «вихід з FAILSAFE: …» (`drive_fsx_text`), покрити тестами обидві причини.
- **Verdict:** Fix now.

### F3 — [stage-1] Успішна відповідь `arm` у стенді не називає джерело «стенд»

- **Де:** `components/rover_console/console_hal.c:99`; AC-13; `contracts/cli.md:24`.
- **Суть:** контракт каже, що відповідь `arm` додатково називає джерело керування «стенд». Відповідь лишилася як у фазі 1, тож «стенд» видно лише в `status`.
- **Пропозиція:** дописати «джерело керування: стенд» у відповідь і перевірити тестом.
- **Verdict:** Fix now.

### F4 — [stage-1] Тумблер у `status` ніколи не буває «невідомо»: без кадрів показується «DISARM»

- **Де:** `components/crsf/crsf_core.c:148`, `main/main.c:114`, `test/host/test_crsf.c:405-413`; AC-12; `contracts/cli.md:61`.
- **Суть:** `crsf_intent` без кадрів повертає `CRSF_SW_DISARM`, а `rc_status` показує саме його. Через це гілка «невідомо» (`crsf_core.c:203`) недосяжна, і в стенді `status` неправдиво пише «тумблер: DISARM». Тест сам підставляє `CRSF_SW_UNKNOWN` у view, тобто перевіряє стан, якого реальний ланцюжок не створює.
- **Пропозиція:** брати показ тумблера з бази фронту (`sw_base` через `drive_status_t`) або ставити UNKNOWN, коли кадрів немає чи зв'язок втрачено; тест має йти через реальний ланцюжок.
- **Verdict:** Fix now.

### F5 — [stage-1] NFR «затримка стік → борти ≤ 50 мс» нема чим виміряти

- **Де:** `docs/features/phase3-crsf/acceptance.md:41`; spec §6 (рядок «Затримка "стік → борти"»), sad.md §10 QG-3.
- **Суть:** spec вимагає діагностичних міток у журналі монітора: мітку прийняття кадру задачею `crsf_rx` і мітку запису команди бортам. Прошивка їх не друкує, а чекліст без рішення власника замінює вимір оцінкою «на око». Так NFR випадає з ланцюжка.
- **Пропозиція:** додати діагностичну мітку, яку можна вмикати (наприклад, проріджено, раз на N кадрів), і крок виміру в `acceptance.md`.
- **Verdict:** Fix now.

### F6 — [stage-2] Знакова різниця міток ламається через ≈ 24.8 доби без кадрів

- **Де:** `components/drive/drive_core.c:157`, `:195`; AC-05, AC-08; sad.md §4 (рядок 120).
- **Суть:** `(int32_t)(now - t_ms) <= 500` стає від'ємним, коли кадрів немає ≥ 2^31 мс. Тоді зв'язок вважається «живим», у журнал іде хибне «зв'язок відновлено», а `status` показує «живий». Небезпечного руху немає: без нових кадрів немає фронту, а вихід із FAILSAFE блокує STABILIZING. Але код розходиться з sad.md §4, де сказано, що «різниця беззнакова» і переповнення не впливає.
- **Пропозиція:** порівнювати беззнаково `(uint32_t)(now - t_ms)` для таймера зв'язку і `link_since_ms` (`control` бере `now` після знімка, тож `now ≥ t_ms`); тест з віком > 2^31 мс. Текст sad.md тоді стає правдою, правити його не треба.
- **Verdict:** Fix now.
