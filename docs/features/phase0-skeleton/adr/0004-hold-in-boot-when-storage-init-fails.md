# 0004 — Лишатися в BOOT з працюючою консоллю, якщо сховище не ініціалізується

- **Status:** Accepted
- **Date:** 2026-10-17
- **Deciders:** Розробник проєкту + Claude (сесія design, 2026-10-17)

## Context

AC-12 визначає очищення сховища лише для двох результатів ініціалізації: «немає вільних сторінок» і «знайдено новішу версію». Для будь-якої іншої помилки (або якщо ініціалізація провалилась і після очищення) таблиця переходів не має ходу з BOOT у FAULT, а документ 02 §5 забороняє `abort()`. Поточний код викликає `ESP_ERROR_CHECK`, який при `PANIC_PRINT_REBOOT` дає нескінченний цикл перезавантажень. Закриває відкрите питання про невдалу ініціалізацію зі §8 специфікації. Фаза 0 сховище не використовує.

## Decision drivers

- Документ 02 §5: «будь-яка помилка → перехід у FAILSAFE/FAULT, ніколи не `abort()`».
- Таблиця переходів (AC-06) не дозволяє BOOT→FAULT.
- Розробник має бачити причину збою, а не цикл перезавантажень.

## Considered options

1. **Лишитися в BOOT з консоллю** — консоль стартує до ініціалізації сховища; при збої автомат не виходить із BOOT, `status` показує «сховище недоступне» й причину.
2. **Продовжити до DISARMED без сховища** — стартувати далі, позначивши сховище недоступним; фаза 0 сховища не потребує.

## Decision outcome

**Chosen:** варіант 1. Стан BOOT чесно показує, що старт не завершений; DISARMED означає «база готова». Консоль і сторожовий таймер стартують до сховища, тож діагностика можлива.

## Consequences

**Positive**
- Немає циклу перезавантажень і немає `abort()`.
- Збій видно в `status`; DISARMED не обіцяє того, чого немає.

**Negative**
- Щоб із «застряглого» BOOT можна було вийти програмно, команда `reboot` дозволена також у BOOT (рішення Розробника 2026-10-17, AC-05 оновлено); `wdt-test` у BOOT лишається забороненим.
- Збій, що не стосується фази 0 (сховище не використовується), блокує вихід у DISARMED.

**Neutral**
- Коли фази 1+ почнуть використовувати сховище, поведінку можна переглянути (перехід у FAULT після появи ребра BOOT→FAULT).
